# StayMatch

**StayMatch** — прототип AI travel agent для хакатона **О!Хакатон 2026**, трек **«О!дин запрос»**.

Идея проекта: пользователь описывает поездку обычным человеческим языком, а агент сам уточняет только недостающие критичные параметры, предлагает несколько объяснимых вариантов, позволяет изменить условия поездки и доводит сценарий до демонстрационного бронирования.

> Репозиторий: https://github.com/ostrovok-hackathon-2026/staymatch

---

## Что умеет StayMatch

### 1. Понимает естественный запрос

Пример:

> Хотим в Анталью из Москвы с детьми с 10 по 17 ноября, бюджет до 400 тысяч.

Агент извлекает:

- город отправления;
- направление;
- точные даты;
- длительность;
- бюджет;
- состав группы;
- наличие детей;
- дополнительные ограничения и предпочтения.

Если данных недостаточно, StayMatch задаёт **минимальные уточняющие вопросы по одному**, а не превращает диалог в длинную анкету.

Например:

- «Сколько взрослых поедет?»
- «Сколько детей поедет?»
- «Сколько лет детям?»
- «Из какого города вы планируете отправляться?»
- «На сколько ночей планируется поездка?»

---

## 2. Учитывает состав группы

StayMatch различает:

- одного взрослого;
- несколько взрослых;
- одного ребёнка;
- несколько детей;
- возраст каждого ребёнка.

Например:

> 2 взрослых · 3 ребёнка · 1, 5 и 9 лет

Возраст детей используется в демонстрационном расчёте транспорта и трансфера.

---

## 3. Подбирает направление

Если пользователь не указал конкретный город, StayMatch ранжирует доступные направления по требованиям запроса.

Учитываются:

- море;
- тёплая погода;
- тёплое море;
- семейность направления;
- длительность дороги;
- ориентировочный бюджет;
- наличие доступного маршрута.

Если направление указано явно, оно считается **жёстким ограничением** и не заменяется другим городом.

---

## 4. Проверяет запрос «тёплое море»

Для демонстрационного набора данных действует правило:

**тёплое море = температура воды не ниже +23 °C.**

Пример для ноября:

- Дубай — около +28 °C;
- Анталья — около +23 °C;
- Сочи — ниже порога и исключается из такого запроса.

Если температура находится на нижней границе, агент показывает предупреждение:

> Температура моря около +23 °C — это нижняя граница заданного условия «тёплое море».

---

## 5. Ранжирует отели и объясняет выбор

Для каждого варианта показываются:

- Match Score;
- основные причины соответствия;
- риски и ограничения;
- стоимость;
- число необходимых номеров;
- трансфер;
- итоговая стоимость поездки.

Блок **«Что важно учесть»** показывается только тогда, когда действительно есть риск, ограничение или компромисс.

---

## 6. Рассчитывает необходимое количество номеров

В синтетических данных у каждого отеля указана максимальная вместимость номера.

Если вся группа не помещается в один номер, StayMatch автоматически рассчитывает необходимое число номеров.

Пример:

- 2 взрослых;
- 3 ребёнка;
- вместимость номера — 4 гостя;

→ требуется **2 номера**.

Стоимость размещения пересчитывается с учётом:

- количества номеров;
- количества ночей.

---

## 7. Рассчитывает авиабилеты по пассажирам

В MVP используется **синтетическая демонстрационная тарифная модель**.

Для перелёта:

- взрослый / пассажир 12+ — **100% базового тарифа**;
- ребёнок 2–11 лет — **75% базового тарифа**;
- младенец до 2 лет — **10% базового тарифа**.

Это не реальные правила конкретной авиакомпании. Модель используется для демонстрации логики персонального расчёта стоимости.

---

## 8. Рассчитывает трансфер по пассажирам

Для трансфера в MVP действует отдельная синтетическая модель:

- взрослый / пассажир 12+ — **100% базового тарифа**;
- ребёнок 2–11 лет — **50% базового тарифа**;
- младенец до 2 лет — **0%**.

---

## 9. Перепланирует уже собранную поездку

После получения рекомендаций пользователь может изменить условия обычным сообщением.

Примеры:

> А если поехать на два дня позже?

> Давайте не на 7, а на 10 ночей.

> Давайте с 12 ноября.

> Давайте бюджет до 120 тысяч.

> Мы решили взять с собой собаку.

StayMatch сохраняет контекст и пересобирает поездку без повторного заполнения уже известных параметров.

Поддерживаются:

- изменение бюджета;
- изменение длительности;
- изменение даты начала;
- сдвиг всей поездки на несколько дней;
- новый диапазон дат;
- добавление или исключение питомца.

---

## 10. Учитывает питомца как hard filter

Если пользователь сообщает, что едет с собакой, кошкой или питомцем, StayMatch оставляет только отели, где разрешено размещение с животными.

Примеры распознаваемых формулировок:

- «Берём собаку»;
- «Поедем с собакой»;
- «С нами кошка»;
- «Без собаки»;
- «Собака не едет».

---

## 11. Собирает поездку в корзину

После выбора варианта StayMatch формирует корзину:

- транспорт;
- отель;
- количество номеров;
- трансфер;
- состав путешественников;
- даты;
- итоговая стоимость.

Перед оформлением итоговая сумма повторно проверяется внутри приложения.

---

## 12. Демонстрационное бронирование

MVP заканчивается mock checkout:

1. пользователь выбирает вариант;
2. проверяет корзину;
3. вводит данные основного путешественника;
4. подтверждает оформление;
5. получает экран «Бронирование подтверждено».

Реальная оплата и бронирование во внешних системах не выполняются.

# Пример полного сценария

Запрос:

> Хотим в Анталью из Москвы с детьми с 10 по 17 ноября, бюджет до 400 тысяч.

StayMatch уточняет:

> Сколько взрослых поедет?

Ответ:

> 2

Далее:

> Сколько детей поедет?

Ответ:

> 3

Далее:

> Сколько лет детям?

Ответ:

> 1, 5 и 9 лет

Для одного из демонстрационных вариантов агент рассчитывает:

- путешественники: **2 взрослых · 3 ребёнка**;
- перелёт: **93 600 ₽**;
- отель: **152 000 ₽**;
- требуется **2 номера**;
- трансфер: **6 750 ₽**;
- итог: **252 350 ₽**.

После этого пользователь может, например, написать:

> А если поехать на два дня позже?

StayMatch переносит период с **10–17 ноября** на **12–19 ноября**, сохраняя длительность и состав группы.

# Архитектура

Приложение построено как небольшой agentic workflow с сохранением состояния диалога.

Основные слои:

```text
Пользовательский запрос
        ↓
Парсинг и нормализация
        ↓
Уточнение недостающих параметров
        ↓
TripRequest
        ↓
Подбор направления
        ↓
Подбор транспорта
        ↓
Подбор и ранжирование отелей
        ↓
Проверка вместимости / количества номеров
        ↓
Расчёт стоимости
        ↓
Объяснимые рекомендации
        ↓
Перепланирование
        ↓
Корзина
        ↓
Mock checkout
```

### Основные модули

```text
trip_models.py       — модели данных
trip_engine.py       — парсинг запроса и подбор направления
agent_logic.py       — уточняющие вопросы и обновление параметров
agent_flow.py        — состояние и сценарий диалога
trip_planner.py      — сборка и ранжирование поездок
replan_logic.py      — изменение уже собранного плана
checkout_logic.py    — корзина и mock checkout
app.py               — Streamlit UI
seed_data.py         — генерация синтетических данных
```

# Почему без внешнего LLM API

Для конкурсного MVP используется **детерминированный парсер + stateful agent workflow**.

Это сделано намеренно:

- приложение работает полностью локально;
- не требует платного API;
- результат воспроизводим для жюри;
- нет риска rate limit / отсутствия API key;
- можно стабильно тестировать unseen-сценарии в пределах поддерживаемой грамматики.

Архитектура допускает замену детерминированного слоя понимания запроса на LLM / structured extraction без изменения остальных модулей планирования.

# Данные

Организаторы не предоставляли API, MCP или датасет Ostrovok.

Поэтому MVP использует **синтетический демонстрационный набор данных**, созданный специально для проекта.

В `data/` находятся:

```text
destinations.csv
hotels.csv
transport.csv
transfers.csv
```

Данные содержат демонстрационные:

- направления;
- температуры;
- температуры моря;
- отели;
- рейтинги и характеристики;
- pet-friendly признаки;
- вместимость номеров;
- цены;
- маршруты;
- тарифы транспорта;
- трансферы.

**Все цены и тарифные коэффициенты являются синтетическими и не являются офертой или актуальными тарифами реальных поставщиков.**

# Запуск через Docker

Требования:

- Docker Desktop или Docker Engine;
- Docker Compose.

Создайте `.env` из примера:

```bash
cp .env.example .env
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

Запуск:

```bash
docker compose up --build
```

После запуска:

### Приложение

http://localhost:8080

### Health check

http://localhost:8080/health

Ожидаемый ответ:

```json
{"status":"ok"}
```

Остановка:

```bash
docker compose down
```

# Ограничения MVP

Это хакатонный прототип, поэтому:

- используются синтетические данные;
- нет подключения к реальной системе бронирования;
- нет реальной оплаты;
- нет проверки реального остатка номеров;
- нет актуальных тарифов авиакомпаний;
- нет реальных правил детских тарифов конкретных перевозчиков;
- нет live API транспорта и трансферов;
- NLU-слой детерминированный и покрывает ограниченный набор естественных формулировок.
